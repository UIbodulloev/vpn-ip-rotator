# vpn-ip-rotator

Меняет IP-адрес VPN-сервера на UpCloud, когда его заблокировал ТСПУ. Замечает
блокировку сам, отличает её от блока протокола, переписывает DNS-запись и
рапортует в Telegram. Управление — целиком из чата.

Написан под связку **Amnezia 2.0 (VLESS+Reality и AmneziaWG) + UpCloud +
Cloudflare**, но привязан только к API провайдеров, а не к конкретному VPN.

---

## Три ограничения, из которых выросла конструкция

Их стоит понять до установки — они объясняют, почему всё устроено именно так.

**1. Сервер не видит собственную блокировку.** Из Европы он доступен всегда.
Блокировка существует только со стороны России, поэтому наблюдатель обязан
стоять в России. Это и есть роль вашего РФ-сервера.

**2. С российского хостинга не работает Telegram API.** Бот не может ходить в
`api.telegram.org` напрямую, и доступность `api.upcloud.com` оттуда тоже не
гарантирована. Поэтому агент ходит наружу через маленький воркер на Cloudflare.

**3. Смена основного IP требует остановленного сервера.** В документации
UpCloud: *«If a MAC address is specified, the server … must be in `stopped`
state»*, а удаление сервера — тем более. Скрипт, живущий на самом VPN-боксе,
остановил бы сам себя на втором шаге из семи. Оркестратор обязан быть снаружи.

Пункты 1 и 3 сходятся в одном месте: агент живёт на РФ-сервере. Пункт 2
закрывает релей.

```
┌──────────── Россия ────────────┐   ┌── Cloudflare edge ──┐   ┌──── UpCloud ────┐
│ ваш существующий РФ-сервер     │   │                     │   │                 │
│                                │   │  Worker «relay»     │   │  VPN-сервер     │
│  vpn-rotator (systemd)         │   │  ─ /tg  → telegram  │   │  xray :443      │
│   ├ пробы ────── прямой TCP ───┼───┼─────────────────────┼──▶│  awg  :35206    │
│   ├ бот  ───┐                  │   │  ─ /uc  → upcloud   │──▶│  ключей нет     │
│   ├ движок ─┼── HTTPS через ───┼──▶│  ─ /cf  → cloudflare│   └─────────────────┘
│   └ секреты ┘   релей          │   │                     │──▶  DNS вашей зоны
└────────────────────────────────┘   └─────────────────────┘
```

**На VPN-сервере не появляется ни одного скрипта и ни одного ключа.** Машина,
которую с наибольшей вероятностью будут ковырять, не хранит доступов вообще.

## Может ли ТСПУ заблокировать вас по домену?

Короткий ответ: домена в вашем трафике нет, но он виден в DNS-запросах клиентов.

AmneziaWG — обфусцированный UDP без SNI. VLESS Reality предъявляет чужой SNI
(`www.googletagmanager.com` или какой вы выбрали), а не ваш домен. Заблокировать
`vpn.example.com` по SNI-инспекции технически не за что.

Домен виден только когда клиент его резолвит. Чтобы ТСПУ начал резать эти
ответы, домен должен попасть в реестр. Три пути, из которых один неочевидный:

1. **Certificate Transparency.** Любой выпущенный на домен TLS-сертификат
   (Let's Encrypt в том числе) публикуется в открытые CT-логи и находится через
   crt.sh за минуту. Reality сертификат не требует — **не выпускайте сертификат
   на VPN-домен и на `*.вашазона`.**
2. Публикация конфигов в открытых чатах и каналах.
3. Перебор поддоменов, если apex-домен где-то засветился.

Порядок реальных угроз: блок `IP:порт` → блок по фингерпринту протокола → блок
домена. Ротация лечит первое. Второе она не лечит, и детектор специально учится
это различать, чтобы не жечь адреса впустую. От третьего страхует запасной
домен в другой зоне у другого регистратора — заведите его заранее.

## Режимы смены адреса

| Режим | Даунтайм | Деньги | Меняет зону | Меняет подсеть | Нужен SSH |
|---|---|---|---|---|---|
| `replace-ip` | ~2–3 мин | нет | нет | нет | нет |
| `recreate` | ~5–10 мин в своей зоне, 20–40 мин в другой | нет | **да** | **да** | нет |
| `floating` | **0** | ~$3.5/мес за адрес | нет | нет | да |

### `replace-ip` — рабочая лошадка

Стоп → новый IPv4 на MAC существующего интерфейса → освободить старый → старт.
При загрузке адрес приезжает по DHCP, netplan трогать не нужно.

Порядок «сначала выдать новый, потом освободить старый» не косметический:
наоборот интерфейс на секунду остаётся без адресов. Если освободить старый не
удалось, сервер всё равно поднимается, **DNS не трогается**, приходит алерт.

### `recreate` — когда выжжена подсеть или нужен переезд

Стоп → шаблон системного диска → новый сервер из шаблона → обновить DNS →
удалить старый. Новый адрес при создании сервера бесплатный, а неиспользованное
время старого возвращается на счёт — это дешевле плавающего адреса.

Шаблон тянет за собой **всё**: ключи AmneziaWG и Reality, базу клиентов, ваш
swapfile, SSH host key и `authorized_keys`. Клиентские конфиги после
пересоздания остаются валидными — меняется только адрес.

Старый сервер удаляется **после** того, как новый поднялся и DNS переписан.
Если что-то сорвалось раньше — старый просто запускается обратно, и вы остаётесь
ровно там, где были. Последний шаблон сохраняется как точка отката (`/rollback`).

Кросс-зонный переезд: диск клонируется в целевую зону (`POST
/1.3/storage/{uuid}/clone` с параметром `zone`), там из него делается шаблон, и
уже из него поднимается сервер. Это самый долгий шаг, полчаса — норма.

### `floating` — если даунтайм неприемлем

Плавающий адрес заказывается на **живом** сервере, поднимается по SSH через
`/etc/netplan/99-floating.yaml` + `netplan apply`, соединение не рвётся.

Важная оговорка: агент ходит на сервер по SSH, а если заблокирован сам адрес, то
и SSH до него не достучится. Режим рассчитан на два случая: профилактическая
ротация до блокировки и блокировка только рабочего порта при живом 22-м — ровно
тот случай, который детектор и распознаёт. Агент пробует по очереди текущий
плавающий, основной и IPv6; если не отвечает ни один — честно отказывается и
предлагает `replace-ip` или `recreate`.

Основной DHCP-адрес при этом не трогается (его нельзя освободить у работающего
сервера) — освобождается только предыдущий плавающий.

### `auto` — лестница эскалации

1. Первая блокировка → `replace-ip`.
2. Новый адрес умер меньше чем за `escalate_after_hours` → дело не в адресе, а в
   подсети или протоколе → `recreate` в следующую зону из `zone_rotation`.
3. Заблокировано и после переезда → **стоп**. Дальше гонять адреса бессмысленно:
   приходит алерт с предложением менять порт, `dest`/SNI Reality или транспорт.

## Установка

### Шаг 1. Релей

Без node — только `curl` и `python3` (скрипт сам сгенерирует ключ, зальёт
воркер, создаст DNS-запись и маршрут, проверит доступ):

```bash
cd relay
export CF_DEPLOY_TOKEN=$(cat ~/.cf-deploy-token)
./deploy.sh relay.example.net
```

Токен для развёртывания — отдельный, с правами `Workers Scripts: Edit`,
`Workers Routes: Edit`, `DNS: Edit`, `Zone: Read`; **после развёртывания
отзовите его**. Вариант через `wrangler` тоже поддержан — см.
[relay/README.md](relay/README.md).

Два обязательных условия: **отдельный домен** (не тот, что обслуживает VPN — иначе
блокировка домена выносит разом и VPN, и канал управления) и **не `*.workers.dev`**
(его в России регулярно режут). Подробности — в [relay/README.md](relay/README.md).

### Шаг 2. Агент на российском сервере

```bash
git clone https://github.com/UIbodulloev/vpn-ip-rotator.git
cd vpn-ip-rotator
sudo ./install.sh
```

Установщик создаёт системного пользователя `vpnrotator`, venv в
`/opt/vpn-rotator`, юнит systemd и спрашивает четыре бутстрап-значения:
`RELAY_URLS`, `RELAY_KEY`, `TG_BOT_TOKEN`, `TG_ADMIN_ID`. Ничего из уже
работающего на сервере он не трогает.

Стартует с `dry_run = true`: пробы идут, уведомления приходят, ротации только
имитируются.

### Шаг 3. Доступы — из Telegram

Напишите боту `/setup`. Мастер ведёт по шагам и показывает прогресс; руками вы
печатаете **только два токена**, всё остальное выбирается кнопками из того, что
вернул API.

```
⚙️ Настройка — 2 из 4

✅ 1. Токен UpCloud
✅ 2. Сервер — 203.0.113.11
▫️ 3. Токен Cloudflare
▫️ 4. Домен и DNS-запись

[ ▶️ Дальше: Токен Cloudflare ]
```

| Шаг | Что делаете |
|---|---|
| 1. Токен UpCloud | присылаете токен, бот сразу его проверяет |
| 2. Сервер | **жмёте кнопку** — бот показал список серверов аккаунта |
| 3. Токен Cloudflare | присылаете токен, бот проверяет |
| 4. Домен и запись | **жмёте кнопку** — бот показал зоны, потом A-записи; домен и AAAA подставляются сами |

Необязательные ключи спрятаны за отдельной кнопкой и каждый подписан, что он
включает: админ-токен UpCloud (чтобы `recreate` работал под субаккаунтом),
логин субаккаунта, AAAA-запись, приватный SSH-ключ (только для `floating`) и
публичный SSH-ключ (прописать новому серверу при `recreate`).

Справка живёт прямо в боте: `/guide` — как это работает, чем отличаются режимы,
какие ключи нужны и зачем, где их взять, что проверить до боевого режима.

Сообщение с токеном бот удаляет сразу после чтения.

> Оговорка без прикрас: сообщение удаляется из чата, но до удаления успевает
> полежать на серверах Telegram. Если это неприемлемо — те же значения вводятся
> с консоли: `sudo -u vpnrotator /opt/vpn-rotator/venv/bin/python -m rotator setup --local`.

#### UpCloud

Заведите **субаккаунт** и выдайте ему права только на VPN-сервер:
`target_type: server`, `target_identifier: <UUID сервера>`, `options.storage: yes`.
Под субаккаунтом выпустите токен `ucat_…` — Bearer, срок до 8760 часов,
поддерживает `allowed_ip_ranges` (впишите туда IP вашего РФ-сервера).

Агент использует: `GET /1.3/server/{uuid}`, `/1.3/zone`, `/1.3/plan`,
`POST /1.3/server/{uuid}/stop|start`, `POST /1.3/server`, `DELETE /1.3/server/{uuid}`,
`POST /1.3/ip_address`, `DELETE /1.3/ip_address/{ip}`,
`POST /1.3/storage/{uuid}/templatize|clone`, `GET|DELETE /1.3/storage/{uuid}`.

> **Подводный камень с правами.** В UpCloud API нет типа прав на IP или диски —
> права выдаются на `server`. Для `replace-ip` этого хватает. Но `recreate`
> создаёт **новый** сервер, которого в правах субаккаунта нет, и следующая
> ротация упрётся в 403. Решения два: либо задать `UPCLOUD_ADMIN_TOKEN` (токен
> основного аккаунта, ограниченный `allowed_ip_ranges`) — тогда агент выдаёт
> права на новый сервер сам через `POST /1.3/permission/grant`, либо выдавать их
> руками после каждого переезда. `/check` предупредит, если этого не сделать.

#### Cloudflare

Токен (**не** Global API Key) с единственным правом `Zone → DNS → Edit`,
Zone Resources → Include → Specific zone → ваша зона.

`CF_ZONE_ID` возьмите со страницы обзора домена. `CF_A_RECORD_ID` и
`CF_AAAA_RECORD_ID` не ищите руками — пришлите боту `/auto`, он найдёт их по
домену из конфига. Права `Zone → Read` при этом не нужны: чтение записей своей
зоны входит в `DNS → Edit`.

#### Telegram

Бот у `@BotFather`, ваш `chat_id` — у `@userinfobot`. Команды от любого другого
чата игнорируются молча.

#### SSH — только для `floating`

`SSH_KEY_PATH` — приватный ключ на РФ-сервере. Заведите **отдельный**, не тот,
которым ходите руками, и ограничьте его на VPN-сервере в `authorized_keys`:

```
command="/usr/local/bin/apply-floating-ip",no-port-forwarding,no-agent-forwarding,no-pty ssh-ed25519 AAAA...
```

Тогда компрометация РФ-сервера не даёт shell на VPN-боксе.
`SSH_PUBKEY` — публичный ключ, который пропишется новому серверу при `recreate`.

### Шаг 4. Клиенты — до первой ротации

**Без этого шага смена DNS ничего не переключит.** Приложение Amnezia принимает
только IPv4 при добавлении сервера ([issue #948][i948] закрыт как «not planned»),
поэтому домен подставляется в конфиги руками — один раз.

[i948]: https://github.com/amnezia-vpn/amnezia-client/issues/948

1. **AmneziaWG** — в `.conf` заменить адрес на домен:
   `Endpoint = vpn.example.com:35206`
2. **VLESS Reality** — заменить хост в ссылке, SNI не трогать:
   ```
   vless://<uuid>@vpn.example.com:443?security=reality&sni=www.googletagmanager.com&fp=chrome&pbk=<public-key>&sid=<short-id>&flow=xtls-rprx-vision&type=tcp#vpn
   ```
   Публичный ключ Reality — из приватного, который лежит в `server.json`:
   `docker exec amnezia-xray xray x25519 -i <privateKey>`
3. **TTL A-записи — 60**, не `Auto` (Auto означает 300). Proxy выключен: через
   оранжевое облако VPN не ходит.
4. Раздайте каждому **два** конфига: основной по домену и запасной по IP. Если
   ТСПУ начнёт подменять DNS, запасной останется рабочим.
5. Заведите запасной домен в другой зоне у другого регистратора, A-запись на тот
   же адрес, конфиги подготовьте — но не раздавайте.

### Шаг 5. Боевой режим

Когда `/check` зелёный и проверка из следующего раздела пройдена — уберите
`dry_run` в `/etc/vpn-rotator/config.toml`, `systemctl restart vpn-rotator`,
и `/mode auto` в чате.

## Проверка

Порядок важен: сначала то, что ничего не ломает.

1. **`/check`** — все доступы зелёные, сервер читается по API.
2. **Домен раньше автоматики.** Подключитесь AmneziaWG и Hiddify по домену —
   обоими протоколами, с телефона по мобильному интернету.
3. **Детектор вхолостую.** При `dry_run = true` зарежьте на РФ-сервере
   исходящий трафик к VPN:
   ```bash
   sudo iptables -A OUTPUT -d <IP сервера> -p tcp --dport 443 -j DROP
   sudo iptables -A OUTPUT -d <IP сервера> -p tcp --dport 22  -j DROP
   ```
   Через ~5 минут должен прийти вердикт «блокировка IP» и сообщение, что
   ротация сработала бы. Снимите правила (`iptables -D OUTPUT …`) — счётчик
   неудач обнулится.
4. **Дискриминация — ключевой тест.** Зарежьте только 443, оставив 22.
   Вердикт обязан быть «блок порта/протокола», ротация **не** предлагается.
   Именно это защищает от бессмысленного сжигания адресов.
5. **`replace-ip` вживую.** `/rotate` → `replace-ip`. Замерьте даунтайм. Потом:
   `dig +short vpn.example.com @1.1.1.1` отдаёт новый адрес; на сервере
   `docker ps` показывает контейнеры `Up`; клиенты переподключаются **без
   правки конфигов**; старого адреса нет в `GET /1.3/server/{uuid}`.
6. **`recreate` в свою зону.** Проверьте, что работают **старые** конфиги
   (ключи приехали в шаблоне), swap на месте (`free -m`), контейнеры подняты,
   старый сервер и его диск удалены, шаблон остался.
7. **`recreate` в другую зону.** Отдельно замерьте время кросс-зонного клона и
   задержку до новой локации.
8. **Устойчивость.** `systemctl restart vpn-rotator` посреди ротации — состояние
   поднимается из `state.json`, дублирующая ротация не стартует. Выключите
   релей — агент уходит в ретраи, ничего не разрушая.

Тесты кода гоняются без единого реального доступа, на фейковом API:

```bash
python3 -m unittest discover -s tests -v
```

## Команды бота

| Команда | Что делает |
|---|---|
| `/status` | адрес, зона, план, состояние сервера, последние пробы, счётчики |
| `/probe` | прогнать пробы сейчас и показать вердикт |
| `/ip` | что у сервера по API и что реально стоит в DNS (сверяет) |
| `/rotate` | выбор режима, для `recreate` — выбор зоны, затем подтверждение |
| `/mode` | режим автоматики: `auto`, `replace-ip`, `recreate`, `floating` |
| `/zones`, `/plans` | живые списки из UpCloud |
| `/pause`, `/resume` | глушилка автоматики (пробы продолжаются) |
| `/log` | последние строки журнала |
| `/setup`, `/check` | доступы и их валидация |
| `/rollback` | пересоздать сервер из последнего шаблона |

Ход ротации показывается редактированием одного сообщения — по шагам, а не
десятком уведомлений.

## Детектор

Раз в минуту, четыре пробы первого уровня:

| Проба | Смысл |
|---|---|
| **S** — свой канал | TCP до Яндекса. Не прошло — молчим, это ваш интернет |
| **A** — рабочий порт | TCP до `IP:443` |
| **B** — контрольный порт | TCP до `IP:22` |
| **C** — состояние сервера | `GET /1.3/server/{uuid}` через релей |

Вердикты:

- A ❌, B ❌, сервер `started` → **блокировка IP** → ротация
- A ❌, B ✅ → **блок порта/протокола** → алерт, ротации нет
- сервер не `started` → **сервер лежит** → алерт, ротации нет
- контрольный порт отключён в конфиге → вердикт помечается как неуверенный,
  ротация не запускается автоматически

### Уровень 2 — настоящая сессия

Голый TCP не отличает «порт открыт» от «соединение живёт». Если ТСПУ научился
ловить фингерпринт, порт будет открываться, а сессия рваться — и смена адреса
не поможет. Ловится только реальным подключением:

```toml
[detector]
deep_probe = true
# Reality: локальный xray с socks-выходом на ваш сервер
reality_probe_cmd = "curl -sf --max-time 15 --proxy socks5h://127.0.0.1:10808 https://www.gstatic.com/generate_204"
# AmneziaWG: отдельный интерфейс с AllowedIPs = 10.8.1.1/32, трафик не перехватывается
awg_probe_cmd = "/opt/vpn-rotator/bin/awg-handshake-check.sh probe0"
```

Команда должна вернуть 0 при успехе. Проба запускается, только если TCP уже
открыт, — незачем гонять её на мёртвом адресе.

### Предохранители

Без них одна ложная тревога сожжёт десяток адресов:

- `fail_threshold = 5` — пять неудач подряд, а не одна;
- `cooldown_hours = 6` между ротациями;
- `max_per_day = 2`, дальше только ручное подтверждение;
- `/pause`;
- каждая ротация пишется в историю с причиной и снимком проб.

---

## Что где лежит

```
/opt/vpn-rotator/            код и venv
/etc/vpn-rotator/config.toml настройки            (0640)
/etc/vpn-rotator/secrets.env доступы              (0600, владелец vpnrotator)
/var/lib/vpn-rotator/state.json  состояние и история
```

`state.json` пишется **после каждого шага** ротации: текущий и прошлые адреса,
UUID сервера и шаблонов, счётчики, стадия незавершённой ротации. Падение посреди
`recreate` доигрывается с места остановки, а не начинается заново с удалённым
сервером — на старте агент сам это делает и громко предупреждает.

Юнит запускается под отдельным пользователем с `ProtectSystem=strict`,
`PrivateTmp`, `NoNewPrivileges` и белым списком семейств сокетов.

---

## Чего эта штука не решает

- **Фингерпринт-блок протокола.** Новый адрес отваливается за минуты. Лечится
  сменой порта, `dest` и SNI Reality, транспорта (XHTTP), параметров обфускации
  AmneziaWG. Детектор такой случай распознаёт и ротацию не запускает — но чинить
  придётся руками.
- **Блок подсети целиком.** Внутри одной подсети ротация бессмысленна; ответ —
  `recreate` в другую зону.
- **Режим белых списков.** Если ТСПУ переключат на allow-list, не спасёт ни один
  из этих протоколов.
- **Одна точка наблюдения.** РФ-хостинг и домашние провайдеры фильтруются
  по-разному. Проба с хостинга — ранний сигнал, но не вся картина.

## Доверие и границы

Токены UpCloud, Cloudflare и Telegram проходят транзитом через ваш воркер, где
TLS терминируется на стороне Cloudflare. Свой DNS вы Cloudflare уже доверяете,
так что порог не меняется — но сказать об этом прямо честнее, чем умолчать.
Воркер секретов не хранит и тел запросов не логирует.

Секреты на РФ-сервере защищены правами `0600` и изоляцией systemd — не
шифрованием: ключ для расшифровки всё равно пришлось бы держать рядом, чтобы
сервис поднимался сам. Реальная защита здесь — узкие права токенов:
субаккаунт на один сервер и токен Cloudflare на одну зону с одним правом.
